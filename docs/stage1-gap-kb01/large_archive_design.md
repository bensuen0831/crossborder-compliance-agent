# Large-upload/archive design (not capacity acceptance)

Authorized browser -> durable session -> signed S3 multipart -> verified immutable object -> bounded isolated worker -> existing Knowledge ingestion. Streaming read/write, no giant bytes/base64/API memory body. Policy examples1GiB single,10GiB archive,50GiB expanded,20000 entries,32MiB parts are configurable ceilings, not measured capacity. UI/API distinguish decimal MB/GB and binary MiB/GiB.

Detect ZIP/RAR4/RAR5 signatures, verify integrity and reject encrypted/corrupt/unsupported split archives. Adapter selection proposal: maintained libarchive/bsdtar read support; license/deployment/RAR compatibility must be verified against actual binaries before acceptance (not installed/validated here). Extract via safe argument vectors in isolated no-network worker with CPU/memory/disk/time ceilings, no links, absolute/traversal paths, nested archive allowlist/depth, normalized collision checks, expanded byte/count limits, configured malware scanning, cancellation cleanup. Bound temporary storage and heartbeat/reclaim lease, per-item durable failures and partial success. Excel pairs full normalized paths and verified content hashes; duplicate bytes are candidates for human resolution, not deletion of distinct language/legal versions.

Production S3 multipart, malware scanner, extractor and capacity fixtures are not configured/tested now. Generate actual nonsparse/incompressible large test data outside Git and transfer real bytes for >500MB document and >1GB actual RAR; test resume/cancel/checksum failure/cleanup and record digests, RSS, bytes, durations, task recovery. Do not claim sparse or compressed-small fixtures satisfy capacity gates.
